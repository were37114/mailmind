## 一、产品定位（用户原始需求提炼）

### 1.1 一句话定义

**MailMind 是运行在用户本地的 AI 邮件第二大脑**——自动下载全量历史邮件，用本地大模型构建个人邮件知识库，主动推荐基于邮件数据的智能任务（审批汇总、报价分析、周报生成等），让邮件从"信息洪流"变为"可执行洞察"。

### 1.2 核心差异化（vs Read AI / Clay / Superhuman）

| 维度 | MailMind | Read AI | Clay | Superhuman |
|------|----------|---------|------|------------|
| 数据主权 | **本地处理，原始邮件不离机** | 云端 | 云端CRM | 云端加速 |
| 核心能力 | **场景驱动型主动推荐** | 会议/邮件摘要 | 关系管理 | 邮件提速 |
| 知识库 | **个人邮件知识库（第二大脑）** | 无 | 联系人图谱 | 无 |
| 企业场景 | **审批/周报/报价分析闭环** | 通用摘要 | CRM场景 | 通用效率 |
| 模型架构 | **本地分层（0.5B+7B）+ 可选云端** | 纯云端API | 纯云端API | 规则+轻量AI |

### 1.3 目标用户（P0 → P1）

| 角色 | 核心痛点 | 高频场景 | 付费意愿 |
|------|----------|----------|----------|
| **企业高管**（P0） | 审批邮件漏处理、出差期间积压 | 审批汇总、紧急邮件识别 | 高（企业付） |
| **销售经理**（P0） | 报价/合同邮件散落、跟进遗漏 | 报价分析、客户邮件聚合 | 中高（个人+企业） |
| **项目经理**（P0） | 跨项目邮件碎片化、周报手工写 | 周报生成、待办提取 | 中（企业付） |
| HR/财务/行政（P1） | 面试安排、发票归档 | 信息提取、分类归档 | 中 |

## 三、智能场景推荐系统（核心卖点详细设计）

### 3.1 设计原则：从"被动工具"到"主动助手"

传统邮件AI是"用户问→AI答"。MailMind是"AI分析→主动推送→用户执行"。

### 3.2 推荐触发条件库

| 触发条件 | 推荐场景 | 优先级 | 模型参与 |
|----------|----------|--------|----------|
| 未处理审批邮件≥3封 | "您有{N}封待审批邮件，X封已超24h" | P0 | 7B精筛 |
| 周五16:00+本周汇报邮件≥2 | "生成本周工作周报" | P0 | 7B生成 |
| 同一发件人近3月报价≥3封 | "{name}报价趋势分析" | P1 | 7B分析 |
| 本周讨论邮件≥5封同一项目 | "项目{name}本周讨论摘要" | P1 | 7B摘要 |
| 3天未回复的讨论邮件 | "{N}封邮件待回复提醒" | P2 | 规则 |
| 连续3天审批延迟 | "审批处理效率提醒" | P2 | 规则 |
| 新发件人首次邮件 | "新增联系人{name}" | P2 | 规则 |

### 3.3 推荐排序算法

```
score = w1 × urgency_score       # 紧急度（时间衰减）
      + w2 × relevance_score     # 相关度（分类匹配）
      + w3 × history_score       # 历史偏好（反馈飞轮）
      + w4 × frequency_score     # 频率（同类型邮件数量）

# 权重初始值
w1=0.35, w2=0.30, w3=0.20, w4=0.15

# 反馈飞轮调整
👍: history_score += 0.1
👎: history_score -= 0.2, w3 *= 0.9
🔄: 同类型场景降权，下一优先场景上浮
```

### 4.2 待确认关键决策（⚠️ 需要用户拍板）

**决策1：数据载体选型**

| 方案 | 优势 | 劣势 | 适用场景 |
|------|------|------|----------|
| A. DuckDB（V4路线） | 分析性能强，TPC-H验证JOIN快14x，嵌入式 | FTS索引不自动更新，邮件场景benchmark缺失 | 分析密集型用户 |
| B. Postgres+PGLite（V5/V6路线） | Hybrid Search成熟，邮件Schema已有验证，GBrain直接复用 | 需额外维护pgvector | 已有GBrain投入，通用性更强 |

**推荐**：方案B（Postgres+PGLite），原因：
- V5/V6已基于GBrain完成大量Schema和验证工作
- Hybrid Search（RRF融合）在邮件场景有实测数据（Recall@5≥80%目标）
- 团队已有技术投入，切换成本高
- DuckDB FTS的"索引不自动更新"对邮件实时同步是硬伤

**决策2：模型分层策略**

```
┌─────────────────────────────────────────┐
│  可选云端增强层（用户主动授权）           │
│  复杂推理 / 跨邮箱关联 / 大规模分析       │
│  敏感字段脱敏后上传，结果回传本地         │
├─────────────────────────────────────────┤
│  7B深度分析层（本地量化）                │
│  审批精筛 / 周报生成 / 场景推荐推理       │
│  模型：Qwen2.5-7B-Instruct-GPTQ-Int4    │
│  资源：~4GB显存 / 8GB内存                │
├─────────────────────────────────────────┤
│  0.5B实时分类层（本地）                  │
│  邮件5类分类 / 紧急度判断 / 发件人排序    │
│  模型：Qwen2.5-0.5B-Instruct            │
│  资源：<1GB内存，CPU可跑                 │
├─────────────────────────────────────────┤
│  Embedding层（向量化）                   │
│  邮件语义向量（bge-small-zh-v1.5）       │
│  资源：~200MB RAM                       │
```

**确认**：沿用V4.0-V6.0统一的三层模型架构，本地优先，云端可选。

## 五、Token成本控制方案

### 5.1 核心策略：分层处理，绝大部分零Token

| 处理阶段 | 比例 | 单次成本 | 1万封总成本 | 说明 |
|----------|------|----------|-------------|------|
| 规则过滤 | 100% | 0 tokens | 0 | 正则/关键词，零成本 |
| 轻量NLP（0.5B） | 100% | ~150 tokens | 75万 | 本地模型，无API费用 |
| Embedding | 100% | ~200 tokens | 200万 | 本地bge-small模型 |
| 7B深度提取 | 10% | ~1500 tokens | 150万 | 仅重要邮件触发 |
| 场景推荐生成 | 按需 | ~2000 tokens | 可变 | 用户触发时生成 |
| **总计** | | | **~425万 tokens** | 全本地运行，仅电费 |

### 5.2 关键降本措施

1. **分类用0.5B不用7B** — 节省90%+ token
2. **摘要截断** — 仅传正文前500字给7B
3. **批量处理** — 周报/审批汇总攒批后一次推理
4. **缓存复用** — 同一邮件链只处理最新一封
5. **按需唤醒7B** — 非活跃时卸载，触发时加载
6. **增量索引** — 仅向量化新邮件，不全量重建

**成本估算**：本地模型无API费用，7B模型推理约0.5元/天电费（按0.8元/度）。
