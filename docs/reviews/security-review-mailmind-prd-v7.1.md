# Security 审查报告

## 总体评分：48/100

## 核心结论：No Go

> **判定理由**：PRD 在数据加密、云端增强安全边界、合规完整性三个核心维度存在致命级缺陷。本地存储零加密意味着一旦设备丢失/被盗/多用户共享，全量邮件数据直接暴露；云端增强通道缺乏端到端加密、服务端处理规范、地域限制等关键设计；合规框架仅以"审计日志"敷衍等保2.0，未覆盖身份鉴别、访问控制、数据保密性等强制要求。在修复 Blockers 之前，**不建议进入开发阶段**。

## 详细审查

### 1. 本地处理承诺
**评分：70/100 | 评价：承诺方向正确，但可验证性不足，存在开发期数据泄露风险**

PRD 明确承诺"原始邮件数据不出本机"、"模型推理本地完成"，并强调云端增强需用户主动授权。这些方向是正确的，但存在以下问题：

- **传输加密未明确**：邮件同步引擎通过 IMAP/POP3/Exchange 从邮件服务器拉取数据，PRD **未强制要求 TLS 1.2+/SSL**，也未提及证书固定或 STARTTLS 降级防护。若用户配置不当或邮件服务器不支持加密，邮件内容将在明文网络中传输。
- **开发/测试期数据风险**：Phase 0 决策项提到"优先使用现有 SaaS 邮箱客户邮件（脱敏）还是 Enron 公开数据集"。这意味着**真实的客户邮件可能在开发/测试环境中被处理**。PRD 完全缺失开发环境数据处理规范（匿名化流程、测试数据销毁机制、开发人员访问控制），这是对"本地处理"承诺的系统性破坏——开发机器也是"本机"之外的机器。
- **脱敏与处理的时序矛盾**：L2 脱敏是"异步"的（7B 模型），但分类（0.5B）和规则引擎是"同步"的。这意味着在新邮件到达后的前几百毫秒内，数据以完全原始状态被处理。虽然仍在本地，但如果此时有屏幕截图、调试日志、或其他进程访问，原始数据可能泄露。

**关键证据**：
> "Phase 0 验证数据集：优先使用现有 SaaS 邮箱客户邮件（脱敏）还是 Enron 公开数据集？" —— PRD §11.2
> "L2-模型脱敏（7B 识别，异步）" —— PRD §14.3

### 2. 脱敏策略
**评分：55/100 | 评价：三级分层思路合理，但存在严重时序漏洞、覆盖不全和可绕过性问题**

PRD 设计了 L1/L2/L3 三级脱敏，但存在多个高危漏洞：

- **L1 规则脱敏可轻易绕过**：手机号、身份证等基于正则的脱敏对变形格式无效（如"138 1234 5678"、"一三八12345678"、"138-1234-5678"）。PRD 未提及对 Unicode 变体、全角字符、OCR 抗性变形等的处理。
- **L2 异步脱敏的时序风险**：7B 脱敏是异步运行的，意味着在 L2 完成前，原始数据已被写入数据库、生成向量索引、可能被推荐系统引用。如果云端增强通道在此期间被触发，**未完全脱敏的数据可能被上传**。
- **邮箱域名暴露**：L1 示例 `z*8@company.com` 保留了完整域名。对企业用户而言，域名本身就是敏感信息（可直接推断用户所在公司）。
- **原始数据未脱敏存储**：PRD 明确"脱敏应用范围：周报生成、审批摘要、推荐卡片中的邮件引用均默认脱敏"，但**完全没有提及 .eml 原始文件和数据库中的数据是否脱敏存储**。如果原始文件以明文保存，设备丢失即全量泄露。
- **L3 白名单的逃逸风险**：用户自定义白名单（"如自己的公司名不脱敏"）若配置错误，可能导致批量敏感信息泄露。没有配置校验机制。

**关键证据**：
> "L2-模型脱敏（7B 识别，异步）" —— PRD §14.3
> "周报生成、审批摘要、推荐卡片中的邮件引用均默认脱敏" —— PRD §14.3（注意：只提"引用"脱敏，不提原始数据）

### 3. 合规框架
**评分：50/100 | 评价：法规清单完整，但应对措施严重不足，存在法律风险**

PRD 列出了 GDPR/CCPA/等保2.0/个保法四部法规，但应对措施仅停留在表面：

- **GDPR Article 25（Privacy by Design）缺失**：MailMind 下载"全量历史邮件"构建知识库，这严重违反 GDPR "数据最小化"原则。PRD **未提供用户选择同步范围**（时间窗口、发件人过滤、文件夹选择）的机制，默认全量同步等同于最大范围数据处理。
- **GDPR 数据控制者/处理者角色未定义**：对于企业版，管理员可查看员工审计日志，此时企业是数据控制者，MailMind 是处理者。PRD 未明确这种法律关系，也未提及数据处理协议（DPA）条款。
- **等保2.0 严重不完整**：PRD 仅以"数据本地存储满足'数据不出域'要求；企业版支持审计日志"应对等保2.0。但等保2.0 第三级要求包括：**身份鉴别、访问控制、安全审计、入侵防范、恶意代码防范、数据完整性、数据保密性、备份恢复**。PRD 几乎只覆盖了"安全审计"中的日志功能，其余全部缺失。
- **个保法"单独同意"机制缺失**：《个人信息保护法》第 29 条要求处理敏感个人信息需取得个人的**单独同意**。邮件内容天然包含大量敏感个人信息（健康状况、财务信息、行踪轨迹、生物识别等）。PRD 仅笼统说"云端增强需用户主动授权"，未设计对敏感个人信息的**单独同意**流程，也未定义什么是"敏感个人信息"（与通用个人信息的区别处理）。
- **CCPA "选择退出"机制不足**：CCPA 要求用户有权选择退出个人信息"销售"和"分享"。虽然 MailMind 承诺不销售数据，但"场景推荐"系统的反馈数据（👍/👎）如果用于模型改进并间接影响其他用户，可能构成"分享"。PRD 未提供选择退出机制。

**关键证据**：
> "等保2.0：数据本地存储满足'数据不出域'要求；企业版支持审计日志" —— PRD §14.2
> "个人信息保护法：脱敏规则默认开启；敏感信息自动识别并掩码" —— PRD §14.2（但无"单独同意"设计）

### 4. 遥测与隐私
**评分：45/100 | 评价："零遥测"承诺与产品功能存在内在矛盾，定义模糊不可执行**

PRD 承诺"零遥测设计：默认不收集任何使用数据、崩溃报告、性能指标"。但存在以下问题：

- **与核心功能的矛盾**："场景推荐系统"依赖用户反馈飞轮（👍/👎/🔄）来优化推荐。这本质上就是**使用数据收集**。PRD 未说明这些数据是仅本地存储还是会上传用于模型迭代。如果用于模型迭代（哪怕是聚合后），就构成了遥测。
- **"遥测"未定义**：业界标准区分"必要遥测"（更新检查、安全补丁）和"可选遥测"（使用分析、性能指标）。PRD 说"零遥测"但未定义边界。如果严格执行，连**更新检查**都不能做（因为更新检查会暴露 IP 地址、版本号、请求时间等）。
- **崩溃报告完全放弃的质量风险**：PRD 明确"不收集崩溃报告"。这确实兑现了零遥测，但意味着产品质量问题将难以诊断。更重要的是，如果用户主动提交崩溃报告（如通过邮件），这些报告可能包含内存转储、日志片段，从而泄露邮件内容。PRD 未设计**用户可控的、脱敏后的崩溃报告提交机制**。
- **更新检查的隐私泄露**：即使不做遥测，软件更新检查也需要向服务器发起请求。服务器日志会记录用户 IP、时间、版本，从而构建用户画像。PRD 未提及使用 Tor、CDN 匿名化、或差分隐私等机制。

**关键证据**：
> "零遥测设计：默认不收集任何使用数据、崩溃报告、性能指标" —— PRD §14.1
> "反馈飞轮: 👍: history_score += 0.1, 👎: history_score -= 0.2" —— PRD §2.2（这是使用数据！）

### 5. 云端增强安全
**评分：40/100 | 评价：安全边界严重模糊，关键安全机制全部缺失**

云端增强通道是 PRD 中隐私风险最高的组件，但安全设计几乎空白：

- **传输安全未定义**：PRD 说"仅传输脱敏数据"，但**未说明传输协议**（HTTPS？TLS 版本？）、是否端到端加密、证书固定、中间人攻击防护等。
- **服务端处理规范完全缺失**：PRD 没有说明云端服务器如何处理接收到的数据。数据在服务端是否持久化？是否写入日志？是否在内存中处理？处理完成后是否立即删除？服务端是否也有脱敏流程？**这些全部缺失**。
- **第三方 API 风险未披露**：如果云端增强调用 OpenAI/Anthropic/阿里云等第三方 API，数据将进入第三方基础设施。PRD **完全没有提及**这一点，也没有说明是否与第三方签署了 DPA（数据处理协议）。这是致命的透明度缺失。
- **地域限制缺失**：PRD 未说明云端服务器部署地域。如果数据传输至境外（如美国、新加坡），将直接违反《个保法》第 38 条（跨境数据传输需安全评估或标准合同）和 GDPR 第 44-49 条（跨境传输限制）。
- **Plan B 违背用户自主权**：Plan B 规定"7B 本地跑不通时，云端增强通道提前（Phase 1 引入），本地降级为 0.5B + 规则"。这意味着用户可能**被迫使用云端增强**（否则无法获得完整功能），这与"用户可随时关闭云端通道"的承诺存在本质冲突——关闭等于功能残缺。
- **授权机制模糊**："用户主动授权"是一次性授权还是每次请求授权？授权范围是否可以细化（如只允许周报生成上云，不允许审批上云）？授权有效期多长？是否可以随时撤销？PRD 全部未说明。

**关键证据**：
> "云端增强需用户主动授权，且仅传输脱敏数据" —— PRD §5
> "Plan B：云端增强通道提前（Phase 1 引入），本地降级为 0.5B + 规则" —— PRD §16

### 6. 数据加密
**评分：30/100 | 评价：本地数据零加密保护，这是致命级缺陷**

这是本次审查中**最严重的安全问题**：

- **.eml 文件零加密**：PRD 完全没有提及本地存储的 .eml 文件是否加密。默认情况下，邮件将以明文形式存储在用户磁盘上。如果设备丢失、被盗、送修，或被恶意软件访问，攻击者可以直接读取所有历史邮件。
- **数据库零加密**：PGLite 数据库（含邮件元数据、分类标签、实体信息）和 pgvector 向量索引同样没有加密设计。即使邮件正文在 .eml 中，数据库中的 subject、from、to、摘要等信息同样敏感。
- **密钥管理完全缺失**：如果未来添加加密，密钥如何管理？基于用户密码派生（PBKDF2/Argon2）？使用操作系统密钥链（Keychain/Windows Credential）？支持硬件安全模块？PRD 完全未提及。
- **内存安全未提及**：Tauri 应用在处理邮件时，数据会加载到内存中。是否有内存加密、防转储、防调试机制？PRD 未提及。
- **邮件同步传输加密未强制**：如前所述，PRD 未强制要求邮件同步必须使用 TLS 1.2+。

**关键证据**：
> PRD 全文搜索 "加密" / "encrypt" / "cipher" / "TLS" / "SSL" —— **零命中**。仅在 "Token 成本控制" 表格中出现 "仅电费"，与安全无关。
> "原始邮件数据存储和处理均在用户本机" —— PRD §5（"本机"不等于"安全"）

### 7. 开源审计
**评分：50/100 | 评价：声明具有误导性，开源范围严重缩水**

PRD 声称"开源可审计：核心推理引擎基于开源 llama.cpp，可独立编译验证"。但：

- **混淆了依赖开源与自身开源**：llama.cpp 是开源的，但 MailMind 本身的代码（邮件同步引擎、脱敏逻辑、推荐系统、数据层、UI 层）**是否开源？PRD 未说明**。如果 MailMind 应用本身是闭源的，那么"开源可审计"的声明是**误导性的**——用户只能审计 llama.cpp，无法审计 MailMind 如何处理数据。
- **开源许可证未说明**：如果 MailMind 开源，使用什么许可证？GPL？MIT？Apache？不同许可证对用户权利和商用限制有根本区别。PRD 未提及。
- **代码托管位置未说明**：开源代码托管在哪里？GitHub？Gitee？是否提供可复现的构建流程（SBOM）？PRD 未提及。
- **"可独立编译验证"不等于"可审计"**：用户自己编译 llama.cpp 只能验证推理引擎的行为，无法验证 MailMind 是否在 llama.cpp 之外做了额外的网络请求、数据收集或后门植入。

**关键证据**：
> "开源可审计：核心推理引擎基于开源 llama.cpp，可独立编译验证" —— PRD §14.1

- **多租户隔离缺失**：如果企业版支持团队部署，不同员工的数据如何隔离？管理员能否跨员工搜索邮件？PRD 未说明。

**关键证据**：
> "企业版：专业版+管理后台+权限+审计+云端通道" —— PRD §8
> "等保2.0：数据本地存储满足'数据不出域'要求；企业版支持审计日志" —— PRD §14.2

## 必须修复的问题（Blockers）

### Blocker 1：本地数据加密机制（致命）
**问题**：.eml 文件、PGLite 数据库、向量索引全部以明文存储，设备丢失/被盗/多用户共享即全量泄露。
**必须修复**：
- 设计全量本地数据加密方案（AES-256-GCM 或 ChaCha20-Poly1305）
- 密钥派生方案（Argon2id 从用户密码派生，或集成操作系统密钥链）
- 加密必须在数据写入磁盘前完成，读取时透明解密
- Phase 0 必须包含加密性能基准测试（确保不成为瓶颈）

### Blocker 2：云端增强通道安全架构（致命）
**问题**：传输协议、服务端处理、第三方 API、地域限制、授权机制全部缺失。
**必须修复**：
- 明确传输协议：TLS 1.3 + 证书固定 + 端到端加密（如使用 Sealed Box 或类似机制）
- 明确服务端数据处理规范：内存处理、零持久化、处理完成后立即删除、服务端日志脱敏
- 如果调用第三方 API（如 OpenAI），必须披露并在隐私协议中明确说明
- 明确云端服务器部署地域，承诺不跨境传输（或提供合规的跨境传输机制：标准合同/安全评估）
- 设计细粒度授权机制：按功能授权（周报上云 vs 审批上云）、按时间授权（临时开启 vs 长期开启）、一键撤销

### Blocker 3：合规框架实质性补充（致命）
**问题**：等保2.0、个保法、GDPR 的应对措施严重不足。
**必须修复**：
- **等保2.0**：补充完整第三级要求的全部维度（身份鉴别、访问控制、入侵防范、数据保密性、备份恢复等）
- **个保法**：设计敏感个人信息"单独同意"流程；定义敏感个人信息识别规则；提供数据可携带权（导出）和删除权机制
- **GDPR**：提供数据最小化选项（选择性同步）；明确 Data Controller/Processor 角色；提供 DPA 模板
- **CCPA**：提供"选择退出"机制（即使不销售数据，也需提供明确的选择退出按钮）

## 建议优化项

1. **定义"遥测"边界并设计用户可控的崩溃报告机制**
   - 区分"必要网络通信"（更新检查、安全补丁）和"可选遥测"（使用分析、性能指标）
   - 提供可选的、脱敏后的崩溃报告提交功能（用户明确同意后才发送，且报告内容经过脱敏处理）

2. **修正"开源可审计"声明**
   - 明确 MailMind 本身是否开源（建议核心数据处理层开源）
   - 说明开源许可证和代码托管位置
   - 提供 SBOM（软件物料清单）和可复现构建流程

3. **增强脱敏策略的鲁棒性**
