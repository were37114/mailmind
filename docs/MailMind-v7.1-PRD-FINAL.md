## 一、产品定位

### 1.1 一句话定义

**MailMind 是运行在用户本地的 AI 邮件第二大脑**——自动下载全量历史邮件，用本地大模型构建个人邮件知识库，主动推荐基于邮件数据的智能任务（审批汇总、报价分析、周报生成等），让邮件从"信息洪流"变为"可执行洞察"。

### 1.2 核心差异化（vs Read AI / Clay / Superhuman）

| 维度 | MailMind | Read AI | Clay | Superhuman |
|------|----------|---------|------|------------|
| 数据主权 | **本地处理，原始邮件不离机** | 云端 | 云端CRM | 云端加速 |
| 核心能力 | **场景驱动型主动推荐** | 会议/邮件摘要 | 关系管理 | 邮件提速 |
| 知识库 | **个人邮件知识库（第二大脑）** | 无 | 联系人图谱 | 无 |
| 企业场景 | **审批/周报/报价分析闭环** | 通用摘要 | CRM场景 | 通用效率 |
| 模型架构 | **本地分层（0.5B+7B）+ 可选云端** | 纯云端API | 纯云端API | 规则+轻量AI |

### 1.3 目标用户（P0 → P1）

| 角色 | 核心痛点 | 高频场景 | 付费意愿 |
|------|----------|----------|----------|
| **企业高管**（P0） | 审批邮件漏处理、出差期间积压 | 审批汇总、紧急邮件识别 | 高（企业付） |
| **销售经理**（P0） | 报价/合同邮件散落、跟进遗漏 | 报价分析、客户邮件聚合 | 中高（个人+企业） |
| **项目经理**（P0） | 跨项目邮件碎片化、周报手工写 | 周报生成、待办提取 | 中（企业付） |
| HR/财务/行政（P1） | 面试安排、发票归档 | 信息提取、分类归档 | 中 |

## 二、核心功能架构

### 2.1 MVP功能范围（gstack评审后调整）

**原范围**: 8周，7个功能模块
**调整后**: 6周，4个核心功能（P0 only）

```
MailMind MVP (6周)
├── 📥 邮件同步引擎
│   ├── 全量历史邮件下载（首次）
│   ├── 增量实时同步（后续）
│   └── 多账户支持（企业+个人）
├── 🔍 实时分类引擎（0.5B本地模型）
│   ├── 5类自动分类（审批/通知/讨论/汇报/其他）
│   ├── 紧急程度标记（高/中/低）
│   └── 发件人权重排序（Top20联系人优先）
├── 📋 审批汇总（双层识别+6步闭环）
│   ├── Layer1: 规则引擎（保召回>99%）
│   ├── Layer2: 7B模型精筛（保精度>80%）
│   ├── 三级置信度展示（高/中/低）
│   └── 6步闭环：查看→预览→操作→确认→通知→归档
├── 📊 周报生成（7B模型）
│   ├── 本周总结（确定性推导，不预测）
│   ├── 待跟进项（从邮件提取的明确待办）
│   └── 导出/发送（Word/飞书/邮件）
└── 🎯 智能场景推荐V1（核心卖点）
    ├── 3类场景卡片（审批汇总/周报生成/待办提醒）
    ├── 用户行为反馈飞轮（👍/👎/🔄）
    └── 推荐排序算法（urgency+relevance+history+frequency）

Phase 2 延后功能:
  ❌ 知识库语义搜索（延至Phase 2）
  ❌ 报价分析（延至Phase 2）
  ❌ 实体关系图谱（延至Phase 2）
  ❌ 附件深度理解（延至Phase 2）
  ❌ Outlook插件（延至Phase 2，先做独立客户端）
```

### 2.2 场景推荐系统（核心卖点详细设计）

**设计原则**：从"被动工具"到"主动助手"

**MVP场景库（3类）**：

| 触发条件 | 推荐场景 | 模型参与 |
|----------|----------|----------|
| 未处理审批邮件≥3封 | "您有{N}封待审批，X封已超24h" | 7B精筛 |
| 周五16:00+本周汇报邮件≥2 | "生成本周工作周报" | 7B生成 |
| 3天未回复的讨论邮件 | "{N}封邮件待回复提醒" | 规则 |

**推荐排序算法**：
```
score = 0.35 × urgency_score + 0.30 × relevance_score 
      + 0.20 × history_score + 0.15 × frequency_score

反馈飞轮:
  👍: history_score += 0.1
  👎: history_score -= 0.2
  🔄: 同类型降权，下优先级上浮
```

## 三、技术架构（gstack评审后调整）

### 3.1 架构简化（6层 → 4层）

```
┌──────────────────────────────────────────────────────────┐
│  Layer 4: UI层（Tauri + React）                          │
│  独立桌面客户端，跨平台（Win/Mac/Linux）                  │
├──────────────────────────────────────────────────────────┤
│  Layer 3: Core层（TypeScript）                           │
│  场景推荐引擎 / 审批工作流 / 周报生成器 / 搜索接口        │
├──────────────────────────────────────────────────────────┤
│  Layer 2: 模型调度层（Rust/TypeScript）                  │
│  ┌──────────┐ ┌──────────┐ ┌───────────┐               │
│  │ 0.5B分类  │ │ 7B分析   │ │ Embedding │               │
│  │ llama.cpp│ │ llama.cpp│ │ ONNXRuntime│               │
│  └──────────┘ └──────────┘ └───────────┘               │
├──────────────────────────────────────────────────────────┤
│  Layer 1: 数据层（PGLite + pgvector）                    │
│  邮件元数据表 / 实体关系表 / 全文索引 / 向量索引         │
│  知识库（Markdown Wiki）— MVP阶段简化版                 │
└──────────────────────────────────────────────────────────┘
```

### 3.2 技术选型（gstack:eng推荐）

| 组件 | 选型 | 理由 | 备选 |
|------|------|------|------|
| 桌面客户端 | **Tauri** (Rust+Web) | 比Electron体积小10x，性能更好 | Electron |
| 模型推理 | **llama.cpp** | 本地推理标准，跨平台，CPU/GPU都支持 | ONNX Runtime |
| Embedding | **ONNX Runtime** | 比Python推理快2-5x | transformers |
| 数据库 | **PGLite** (WASM) | 浏览器/桌面都能跑，无需安装Postgres | DuckDB |
| 向量索引 | **pgvector** | Postgres生态，Hybrid Search成熟 | LanceDB |
| 邮件解析 | **mailparser** (Node.js) | 成熟库，编码处理完善 | 自研 |

### 3.3 数据流设计

```
新邮件到达
  ├── [同步引擎] 下载邮件 → 存储原始.eml
  ├── [解析引擎] 提取元数据（发件人/日期/主题/正文）
  ├── [0.5B分类] 5类分类 + 紧急度 → 写入分类标签（同步，<500ms）
  ├── [规则引擎] 触发条件匹配 → 写入事件队列
  ├── [Embedding] 正文向量化 → 写入向量索引（异步，后台）
  └── [7B分析] 仅重要邮件触发 → 实体提取/摘要（异步，后台）

用户查询
  ├── [自然语言] → 语义检索（向量索引）
  ├── [结构化] → SQL查询（PGLite）
  └── [场景推荐] → 规则匹配 + 模型推理
```

### 3.4 核心Schema

```sql
-- 邮件主表
emails (
  id UUID PRIMARY KEY,
  message_id TEXT UNIQUE,
  thread_id TEXT,
  account_id UUID,
  from_name TEXT, from_email TEXT,
  to_list JSONB, cc_list JSONB,
  subject TEXT, body_text TEXT,
  date TIMESTAMPTZ,
  has_attachment BOOLEAN,
  category INT, -- 0-4
  urgency INT, -- 0-2
  confidence FLOAT,
  created_at TIMESTAMPTZ
);

-- 向量索引（pgvector）
email_embeddings (
  email_id UUID PRIMARY KEY,
  embedding VECTOR(768)
);

-- 实体表
entities (
  id UUID PRIMARY KEY,
  email_id UUID,
  entity_type TEXT, -- person/company/project/amount/date
  entity_value TEXT,
  confidence FLOAT
);

-- 场景推荐记录
recommendations (
  id UUID PRIMARY KEY,
  user_id UUID,
  scene_type TEXT,
  trigger_condition TEXT,
  score FLOAT,
  status TEXT, -- shown/clicked/dismissed
  created_at TIMESTAMPTZ
);
```

## 四、Token成本控制方案

### 4.1 分层处理策略

| 处理阶段 | 比例 | 单次成本 | 1万封总成本 | 说明 |
|----------|------|----------|-------------|------|
| 规则过滤 | 100% | 0 tokens | 0 | 正则/关键词，零成本 |
| 轻量NLP（0.5B） | 100% | ~150 tokens | 150万 | 本地模型，无API费用 |
| Embedding | 100% | ~200 tokens | 200万 | 本地bge-small模型 |
| 7B深度提取 | 10% | ~1500 tokens | 150万 | 仅重要邮件触发 |
| 场景推荐生成 | 按需 | ~2000 tokens | 可变 | 用户触发时生成 |
| **总计** | | | **~500万 tokens** | 全本地运行，仅电费 |

### 4.2 降本措施

1. **分类用0.5B不用7B** — 节省90%+ token
2. **摘要截断** — 仅传正文前500字给7B
3. **批量处理** — 周报/审批汇总攒批后一次推理
4. **缓存复用** — 同一邮件链只处理最新一封
5. **按需唤醒7B** — 非活跃时卸载，触发时加载

**成本估算**：本地模型无API费用，7B模型推理约0.5元/天电费。

## 六、验收标准

### 6.1 审批汇总

| 指标 | 目标值 | 测量方法 |
|------|--------|----------|
| 召回率 | >98% | 标注500封审批邮件，漏检率<2% |
| 精确率 | >80% | 规则引擎候选集中误判率<20% |
| F1 | >88% | 综合计算 |
| 识别延迟 | <3s/封 | 0.5B分类<500ms，7B精筛<2.5s |

### 6.2 周报生成

| 指标 | 目标值 | 测量方法 |
|------|--------|----------|
| 事实准确率 | >95% | 人工核对10份周报，事实错误<5% |

| 生成时间 | <30s | 从点击到生成完成 |
| 无"下周计划" | 100% | 自动检测输出中无预测性内容 |

### 6.3 场景推荐

| 指标 | 目标值 | 测量方法 |
|------|--------|----------|
| 点击率 | >20% | 推荐卡片点击/展示比例 |
| 有用反馈率 | >60% | 👍/(👍+👎) |

## 十、gstack双评审意见摘要

### CEO评审结论
- **评分**: 5/6 YC硬问题通过 → **Go（带条件）**
- **关键洞察**: MailMind不是"邮件客户端+AI插件"，而是"邮件驱动的任务管理系统"
- **MVP建议**: 8周7功能 → **6周4功能**（审批汇总+周报生成+场景推荐+分类）
- **担忧**: 本地部署模式下用户付费意愿需验证

### ENG评审结论
- **评分**: B+ → A-（MVP优化后）
- **架构建议**: 6层 → **4层**，知识库延至Phase 2
- **技术栈**: Electron → **Tauri**，Postgres+PGLite确认
- **产品形态**: 双形态并行 → **独立客户端优先**
- **必须补充**: 数据流图、Schema、API接口（已在v7.1中补充）
