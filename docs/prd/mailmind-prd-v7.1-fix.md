## 一、产品定位
### 1.1 一句话定义
**MailMind 是运行在用户本地的 AI 邮件第二大脑**——自动下载全量历史邮件，用本地大模型构建个人邮件知识库，主动推荐基于邮件数据的智能任务（审批汇总、报价分析、周报生成等），让邮件从"信息洪流"变为"可执行洞察"。
### 1.2 核心差异化（vs Read AI / Clay / Superhuman）

| 维度 | MailMind | Read AI | Clay | Superhuman |
|------|----------|---------|------|------------|
| 数据主权 | **本地处理，原始邮件不离机** | 云端 | 云端CRM | 云端加速 |
| 核心能力 | **场景驱动型主动推荐** | 会议/邮件摘要 | 关系管理 | 邮件提速 |
| 知识库 | **个人邮件知识库（第二大脑）** | 无 | 联系人图谱 | 无 |
| 企业场景 | **审批/周报/报价分析闭环** | 通用摘要 | CRM场景 | 通用效率 |
| 模型架构 | **本地分层（0.5B+7B）+ 可选云端** | 纯云端API | 纯云端API | 规则+轻量AI |

### 1.3 目标用户（P0 → P1）

| 角色 | 核心痛点 | 高频场景 | 付费意愿 |
|------|----------|----------|----------|
| **企业高管**（P0） | 审批邮件漏处理、出差期间积压 | 审批汇总、紧急邮件识别 | 高（企业付） |
| **销售经理**（P0） | 报价/合同邮件散落、跟进遗漏 | 报价分析、客户邮件聚合 | 中高（个人+企业） |
| **项目经理**（P0） | 跨项目邮件碎片化、周报手工写 | 周报生成、待办提取 | 中（企业付） |
| HR/财务/行政（P1） | 面试安排、发票归档 | 信息提取、分类归档 | 中 |

**推荐排序算法**：
```plaintext
score = 0.35 × urgency_score + 0.30 × relevance_score 
      + 0.20 × history_score + 0.15 × frequency_score

反馈飞轮:
  👍: history_score += 0.1
  👎: history_score -= 0.2
  🔄: 同类型降权，下优先级上浮

```

## 三、技术架构（gstack评审后调整）
### 3.1 架构简化（6层 → 4层）

| 层级 | 组件 | 技术选型 |
|------|------|----------|
| UI层 | 独立桌面客户端 | Tauri + React |
| Core层 | 业务逻辑 | TypeScript |
| 模型层 | 0.5B/7B/Embedding | llama.cpp + ONNX Runtime |
| 数据层 | 结构化+向量+全文 | PGLite + pgvector |

### 3.2 技术选型（gstack:eng推荐）

| 组件 | 选型 | 理由 | 备选 |
|------|------|------|------|
| 桌面客户端 | **Tauri** (Rust+Web) | 比Electron体积小10x，性能更好 | Electron |
| 模型推理 | **llama.cpp** | 本地推理标准，跨平台，CPU/GPU都支持 | ONNX Runtime |
| Embedding | **ONNX Runtime** | 比Python推理快2-5x | transformers |
| 数据库 | **PGLite** (WASM) | 浏览器/桌面都能跑，无需安装Postgres | DuckDB |
| 向量索引 | **pgvector** | Postgres生态，Hybrid Search成熟 | LanceDB |
| 邮件解析 | **mailparser** (Node.js) | 成熟库，编码处理完善 | 自研 |

### 3.3 数据流设计
**新邮件到达**：
1. 同步引擎下载 → 存储原始.eml
1. 解析引擎提取元数据
1. 0.5B分类（同步，<500ms）→ 写入分类标签
1. 规则引擎匹配触发条件 → 写入事件队列
1. Embedding向量化（异步，后台）→ 写入向量索引
1. 7B分析（异步，后台）→ 仅重要邮件触发
**用户查询**：
- 自然语言 → 语义检索（向量索引）
- 结构化 → SQL查询（PGLite）
- 场景推荐 → 规则匹配 + 模型推理
### 3.4 核心Schema
**邮件主表**：id, message_id, thread_id, account_id, from_name/email, to/cc_list(JSONB), subject, body_text, date, has_attachment, category(0-4), urgency(0-2), confidence, created_at
**向量索引**：email_id, embedding(VECTOR(768))
**实体表**：id, email_id, entity_type(person/company/project/amount/date), entity_value, confidence
**推荐记录**：id, user_id, scene_type, trigger_condition, score, status(shown/clicked/dismissed), created_at
### 3.5 模型调度接口
- classify(email): ClassificationResult — 0.5B实时，同步，<500ms
- analyze(email): Promise — 7B深度，异步，队列
- embed(emails): Promise<EmbeddingResult[]> — Embedding，异步，批量
- healthCheck(): ModelStatus — 健康检查
- loadModel/unloadModel(modelType) — 动态加载卸载

## 五、安全与隐私设计
**安全承诺**：
- ✅ 原始邮件数据存储和处理均在用户本机
- ✅ 本地模型推理全程在用户本机完成
- ✅ 云端增强需用户主动授权，且仅传输脱敏数据
- ✅ 用户可随时关闭云端通道

### 5.1 本地数据加密方案（零知识架构）

**设计原则**：设备丢失即保险箱丢失——无密码则数据不可恢复。

**数据分类分级**：

| 数据类型 | 敏感等级 | 加密要求 | 说明 |
|----------|----------|----------|------|
| 原始邮件 .eml | 🔴 极高 | AES-256-GCM | 邮件正文、附件元数据 |
| PGLite 数据库文件 | 🔴 极高 | AES-256-GCM | 结构化数据、分类标签、实体 |
| 向量索引 | 🔴 极高 | AES-256-GCM | Embedding 向量、HNSW 索引 |
| 模型缓存 | 🟡 中 | 可选加密 | 下载的 GGUF/ONNX 模型文件 |
| 配置/日志 | 🟢 低 | 不加密 | UI 设置、非敏感运行日志 |

**密钥管理架构**：
```
用户登录密码 + 随机盐值 (Salt, 128-bit)
    ↓（Argon2id，内存 64MB，迭代 3 次，并行 4）
主密钥 (Master Key, 256-bit)
    ├─→ HKDF-SHA256 派生 ──→ 加密数据密钥 (DEK, 256-bit)
    │                           ↓（AES-256-GCM，Nonce 计数器模式）
    │                       加密实际邮件数据、数据库、向量索引
    │
    └─→ HKDF-SHA256 派生 ──→ 加密配置密钥 (Config Key, 256-bit)
                                ↓（AES-256-GCM）
                            加密敏感配置（邮箱密码、API Token）
```

**关键设计**：
- **零知识**：服务端/开发者无法访问用户数据，密码不在任何地方存储
- **密码重置 = 数据重置**：忘记密码则所有数据不可恢复（明确告知用户）
- **密钥派生参数**：Argon2id, m=65536, t=3, p=4（OWASP 2023 推荐）
- **盐值管理**：每个用户独立生成 128-bit 随机盐值，存储于本地配置文件中（明文存储盐值，盐值本身不敏感，但必须唯一且不可预测）
- **主密钥 → DEK 派生**：使用 HKDF-SHA256（提取+扩展两阶段），输入主密钥 + 固定上下文字符串（如 "mailmind-dek-v1"），输出 256-bit DEK
- **AES-256-GCM Nonce 策略**：采用计数器模式（Counter Mode），每加密操作递增 96-bit 计数器，计数器值持久化存储于本地元数据文件。计数器上限为 2^32 - 1，达到上限后触发 DEK 轮换
- **DEK 轮换**：支持定期更换 DEK（通过 HKDF 扩展新上下文字符串），旧 DEK 保留用于解密，新 DEK 用于加密，逐步迁移

**加密范围详细说明**：
- 所有 `.eml` 文件写入磁盘前 AES-256-GCM 加密
- PGLite 数据库文件整体加密（WASM 层解密后加载到内存）
- 向量索引文件（pgvector 的 HNSW 索引）加密存储
- 附件文件（下载的原始附件）单独加密
- 邮箱账户密码（IMAP/SMTP 密码）使用 Config Key 加密存储

**性能影响**：
- 加密/解密开销 < 5%（AES-NI 硬件加速）
- 首次启动需要用户输入密码解锁（< 2 秒）
- 运行时数据在内存中明文，进程结束后自动清除（mlock 敏感区域）

### 5.2 云端增强安全规范（可选功能）

**设计原则**：用户完全可控、传输最小化、服务端零持久化。

**传输安全**：
- **TLS 1.3**：强制证书固定（Certificate Pinning），防止中间人攻击
- **传输层强加密 + 零持久化**：数据离开本机前使用临时会话密钥加密（基于 ECDH 协商），服务端解密处理后立即删除，不保留任何明文或密文副本
- **传输内容审计**：每次上传前展示给用户确认（弹窗显示"将上传以下脱敏内容：[摘要]")

**授权机制**：
- **OAuth 2.0 + PKCE**：短期访问令牌（1小时有效期）+ 刷新令牌（7天）
- **最小权限**：令牌仅授权特定操作（如"周报生成"），非全局权限
- **一键撤销**：用户可随时在设置中撤销云端授权，令牌立即失效

**服务端承诺**：
- **零数据持久化**：处理请求后立即删除所有上传数据，不保留任何日志中的原始内容
- **地域限制**：中国区用户数据仅在中国境内服务器处理（阿里云/腾讯云）
- **第三方 API 披露**：明确列出所有调用的外部 API 及其数据处理范围
- **审计报告**：企业版用户可申请数据处理报告（30天内）

**用户控制面板**：
- 云端功能总开关（默认关闭）
- 查看所有历史上传记录（时间、内容摘要、处理结果）
- 一键删除云端所有痕迹（GDPR "被遗忘权"）
- 设置上传频率上限（如"每周最多上传 10 次"）

### 5.3 遥测与隐私边界

**零遥测承诺的精确定义**：
- ✅ **不收集**：使用行为、点击流、性能指标、崩溃堆栈、设备信息
- ✅ **不传输**：任何数据在未经用户明确同意前不出本机
- ⚠️ **必要的本地数据**：场景推荐的 👍/👎 反馈仅存储在本地数据库，用于本地模型排序优化，不上传
- ⚠️ **可选的崩溃报告**：用户可手动选择发送崩溃报告（弹窗询问，默认否），报告内容经 L3 脱敏后上传
- ⚠️ **可选的更新检查**：检查新版本时仅发送"当前版本号"，不发送任何用户标识

**Beta 测试期间的遥测例外（明确条款）**：
- 在 Phase 1 Beta 测试期间（约 100 人 × 2 周），为验证推荐算法效果，需进行 A/B 测试
- **数据范围**：仅收集推荐卡片的展示/点击/停留时长（不含任何邮件内容、用户身份标识）
- **数据存储**：所有 A/B 测试数据存储在**本地**，不上传任何服务器
- **跨用户对比**：采用"本地聚合后匿名上报"模式——每组用户本地计算聚合统计（如"实验组点击率 22%"），仅上报聚合结果，不上报个体行为
- **用户知情**：Beta 测试邀请时明确告知"本次测试将匿名收集推荐效果数据，可随时退出"
- **测试结束后**：所有 A/B 测试数据自动清除，仅保留聚合结论

**数据生命周期**：
- 本地数据：用户删除即永久删除（覆写后释放）
- 缓存数据：模型缓存、临时文件 7 天自动清理
- 备份数据：不支持自动云端备份，用户可手动导出加密备份文件

| **Apple** | Apple Intelligence（设备端 AI），邮件摘要功能 | 18-24 个月 | 提前建立领域知识壁垒（审批/周报场景优化）；开放插件生态 |

**差异化窗口期评估**：
- MailMind 的核心壁垒不是技术（开源模型 + 标准架构），而是**领域场景优化**（审批识别准确率、周报生成质量）+ **隐私合规能力**（等保2.0、零知识架构）
- 建议在 Phase 1 结束时（MVP 上线）即启动**专有规则库积累**和**领域微调模型训练**，形成数据飞轮

### 9.2 开源替代冲击（中概率 / 高影响）

- 开源社区可能出现基于 Ollama + 开源模型的本地邮件 AI 工具
- **应对**：建立品牌 + 用户体验壁垒（审批 6 步闭环、周报一键导出飞书/钉钉等中国本土集成）

### 9.3 邮件服务商 IMAP 限制（中概率 / 高影响）

- Gmail 已逐步限制"安全性较低的应用"的 IMAP 访问
- **应对**：Phase 1 即增加 OAuth 2.0 + Gmail API 备选方案；企业版支持 Exchange Web Services (EWS)

### 9.4 获客成本低估（高概率 / 中影响）

- PRD 中 CAC ¥100 仅计算直接投放成本
- **真实 CAC 估算**：桌面软件获客包含内容营销、SEO、应用商店优化、KOL 合作等，真实 CAC 可能达 ¥200-300
- **应对**：M3 后建立内容营销体系（邮件管理最佳实践博客、案例研究）；优先通过企业版高 LTV 客户摊薄获客成本

本地推理是 MailMind 的核心卖点，必须明确硬件门槛：

## 十四、数据隐私与合规
### 14.1 隐私承诺（技术保障）
- ✅ **原始邮件数据不出本机**：所有 .eml 文件存储在用户本地磁盘，无云端同步

- ✅ **零遥测设计**：默认不收集任何使用数据、崩溃报告、性能指标
- ✅ **开源可审计**：核心推理引擎基于开源 llama.cpp，可独立编译验证
- ✅ **用户可控**：云端增强功能默认关闭，开启需二次确认并展示传输内容

### 14.2 合规框架

| 法规 | 适用场景 | 应对措施 |
|------|----------|----------|
| **GDPR** | 欧盟用户 | 支持"被遗忘权"（一键删除所有本地数据）；无跨境数据传输 |
| **CCPA** | 加州用户 | 不收集/出售用户数据；提供数据导出功能 |

| **个人信息保护法** | 中国用户 | 脱敏规则默认开启；敏感信息（手机号/身份证）自动识别并掩码 |

### 14.4 等保2.0 第三级详细实现（企业版）

| 等保维度 | 控制点 | 具体实现 | 验证方式 | 责任方 |
|----------|--------|----------|----------|--------|

| **安全管理中心** | 系统管理 | 企业版集中管理后台 | 功能测试 | QA |
| **安全管理中心** | 审计管理 | 审计日志不可篡改（哈希链 + 外部锚定） | 完整性验证 | Security |

**审计日志防篡改技术实现**：
- **哈希链结构**：每条日志记录包含前一条日志的 SHA-256 哈希值，形成链式结构，任何单条篡改都会导致后续哈希不匹配
- **外部锚定机制**：
  - 企业版：每日将哈希链根哈希写入 **WORM 存储**（一次写入多次读取，物理不可删改）或 **可信时间戳服务**（如 RFC 3161）
  - 本地版：每小时将根哈希写入本地只读分区（操作系统级只读挂载），或导出到用户指定的外部存储
- **验证方式**：企业版管理员可随时运行完整性校验工具，遍历哈希链验证全部日志未被篡改
- **留存策略**：本地日志 180 天自动归档到加密备份，企业版远程日志服务器留存 1 年

### 22.2 Ground Truth 标注协议

**标注团队**:
- **标注员 A/B**: 2 名独立标注员（需通过标注一致性测试）
- **仲裁员**: 1 名资深 PM（处理 A/B 分歧）
- **一致性要求**: Cohen's Kappa ≥ 0.8

**"审批邮件"定义标准**:
1. **必须包含**: 明确的审批请求语气（"请审批"、"请批复"、"请确认"）
2. **必须包含**: 待审批事项的具体描述（金额、事项、期限至少一项）
3. **排除**: 仅知会/抄送（"请知悉"）、已完成的审批（"已批复"）、讨论性邮件（"你觉得呢"）
4. **边界情况**: 转发待阅 → 不算审批；请示报告 → 算审批

**"事实"定义标准**:
1. **可验证陈述**: 邮件中明确提到的日期、金额、人名、事件状态、交付物
2. **示例**: "3月15日完成项目评审" → 事实（日期+事件）；"项目进展顺利" → 非事实（主观判断）
3. **标注格式**: 每个事实标注为 `[类型:值]`，如 `[日期:2026-03-15]`, `[金额:50000]`, `[事件:完成项目评审]`

**事实准确率计算公式**:
```plaintext
事实准确率 (Precision) = 模型生成的正确事实数 / 模型生成的总事实数
事实召回率 (Recall) = 模型生成的正确事实数 / Ground Truth 中的总事实数
事实 F1 = 2 × (Precision × Recall) / (Precision + Recall)

其中：
- 正确事实 = 模型提取的事实与 Ground Truth 完全匹配（类型+值一致）
- 部分匹配规则：数值格式差异（如 "50000" vs "50,000" vs "五万元"）视为匹配；日期格式差异（如 "2026-03-15" vs "3月15日"）视为匹配
- 幻觉（模型编造的事实）= 错误事实
- 遗漏 = Ground Truth 中有但模型未生成的事实

验收标准：
  - Precision > 95%（说出来的都是对的）
  - Recall > 80%（该说的基本都说到了）
  - F1 > 87%（综合平衡）
```

### 22.3 点击率统计验证方案

**实验设计**:
- **对照组**: 随机推荐（按时间顺序展示前 3 个待办）
- **实验组**: 智能推荐（算法排序的 3 个场景卡片）
- **随机化**: 用户级别随机（50% 对照 / 50% 实验），非同一用户交替

**样本量计算**:
- 目标检测：20% 点击率 vs 15% 基线（随机推荐估计）
- 显著性水平 α = 0.05，统计功效 1-β = 0.8
- 每组需要展示次数：n = 1100（使用比例检验公式）
- **总需求**: 2200 次展示

**Beta 用户规模**:

| 方案 | 用户数 | 展示频率 | 达到 2200 次所需时间 |
|------|--------|----------|----------------------|
| 方案 A | 50 人 | 3 次/天 | 15 天 |
| 方案 B | 100 人 | 3 次/天 | 8 天 |
| 方案 C | 50 人 | 6 次/天 | 8 天 |

**推荐方案**: 100 人 Beta 测试，持续 2 周（含 onboarding 和数据分析）

**"点击"定义**: 用户点开推荐卡片并停留 >3 秒（排除误触）

### 23.2 模型更新回归流程

```plaintext
模型版本更换（如 Qwen2.5-7B v1 → v2）
    ↓
1. 在新模型上运行审批专项集（400 封，Phase 1）或全量数据集（2000-4000 封，Phase 2）
    ↓
2. 对比新旧模型的核心指标
    - 审批召回率变化 > -2% → ❌ 阻止更新
    - 审批精确率变化 > -3% → ❌ 阻止更新
    - 分类准确率变化 > -5% → ❌ 阻止更新
    - 事实准确率变化 > -3% → ❌ 阻止更新
    - 生成时间变化 > +20% → ⚠️ 警告，需人工确认
    ↓
3. 通过则更新，不通过则回退并分析原因

注：Phase 1 模型回归仅跑 400 封审批专项集（节省 ~90% 时间），
    Phase 2 扩展至全量 2000-4000 封
```
