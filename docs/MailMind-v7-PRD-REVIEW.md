## 1️⃣ Paul Graham 6个硬问题

### Q1: 你自己会用吗？多久用一次？
**评估**: ✅ 会每天用

## 2️⃣ 第一性原理分析

### 拆解到本质

**邮件管理的本质是什么？**
- 不是"更好地看邮件"
- 而是"从邮件中提取可执行洞察，减少认知负担"

**第一性原理推导**：
```
1. 用户每天收到50-200封邮件
2. 其中只有10-20%需要用户采取行动
3. 当前方案：用户自己筛选 → 认知负担高 → 遗漏率高
4. 最优解：AI自动筛选+分类+汇总 → 用户只看"需要行动的" → 认知负担低
5. 物理极限：AI理解准确率的上限 ≈ 人类水平（95%+）
6. 结论：只要AI准确率>80%，就有显著价值
```

**关键洞察**：MailMind不是"邮件客户端+AI插件"，而是"邮件驱动的任务管理系统"——邮件是输入，可执行任务才是输出。

### 行业惯例中可以打破的

| 行业惯例 | 为什么可以打破 | MailMind的做法 |
|---------|--------------|---------------|
| 邮件AI=摘要生成 | 摘要只是信息压缩，不是行动驱动 | 场景推荐=直接推送可执行任务 |
| 邮件数据必须上云才能AI分析 | 本地模型已经足够强大 | 本地0.5B+7B分层处理 |
| 邮件客户端就是收件箱 | 收件箱是被动消费，任务列表是主动执行 | 从"收件箱"到"任务中心" |
| 知识库=手动整理 | 邮件数据本身就是最丰富的知识源 | 自动构建个人邮件知识库 |

## 4️⃣ 规模化思维

### 能服务10亿人吗？
**评估**: 不能直接服务10亿人，但可以服务1亿知识工作者
- 全球知识工作者约10亿，其中使用邮件的约5亿
- 中国市场：企业邮箱用户约2亿，目标渗透率1-5% = 200万-1000万用户
- **规模化路径**：先占领B端企业高管市场 → 向下渗透到中层 → 扩展到个人用户

### 网络效应
- **数据飞轮**：用户越多 → 反馈越多 → 推荐越准 → 用户越多 ✅
- **网络效应**：弱（不是社交平台）⚠️
- **品牌效应**：强（成为"AI邮件助手"的代名词）✅

### 边际成本
- 本地模型：边际成本≈0（用户自付电费）✅
- 云端增强：边际成本≈$2-5/用户/月 ✅
- 研发成本：固定，不随用户增长 ✅

# Part 2: gstack:eng 工程评审

## 🏗️ 架构设计评审

### 1. 整体架构评估

**评估**: ✅ 分层清晰，职责明确

```
邮件客户端/插件层 → Core层 → 模型调度层 → 数据存储层 → 知识库层 → 云端层
```

**优点**:
- 分层明确，每一层职责单一
- 插件层和独立客户端共享Core层，复用性好
- 模型调度层解耦了业务逻辑和模型实现

**风险**:
- 6层架构对于MVP来说可能过重
- 建议MVP阶段简化为4层：UI → Core → 模型 → 数据

### 2. 关键技术决策评审

#### 决策1: 数据层选型（Postgres+PGLite vs DuckDB）

**评审结论**: ✅ 推荐 Postgres+PGLite，但需补充理由

| 维度 | Postgres+PGLite | DuckDB | 评审意见 |
|------|----------------|--------|----------|
| 邮件Schema验证 | ✅ 已有V5/V6验证 | ⚠️ V4架构但未实测 | Postgres路线更成熟 |
| Hybrid Search | ✅ RRF融合已有方案 | ⚠️ FTS索引不自动更新 | Postgres更可靠 |
| 分析性能 | ⚠️ JOIN性能一般 | ✅ TPC-H验证快14x | DuckDB分析更强，但邮件场景OLTP为主 |
| 嵌入式 | ✅ PGLite浏览器端可跑 | ✅ 纯嵌入式 | 两者都OK |
| 团队熟悉度 | ✅ 已有GBrain投入 | ❌ 需重新学习 | Postgres风险更低 |
| 向量检索 | ✅ pgvector HNSW | ⚠️ LanceDB性能数字缺失 | pgvector更成熟 |

**ENG建议**: 选择Postgres+PGLite，但保留DuckDB作为分析场景的备选（Phase 2评估）

#### 决策2: 模型分层策略（0.5B+7B+云端）

**评审结论**: ✅ 合理，但需关注资源占用

| 层级 | 模型 | 资源占用 | 评审意见 |
|------|------|----------|----------|
| 0.5B分类 | Qwen2.5-0.5B | <1GB RAM | ✅ CPU可跑，适合所有用户 |
| 7B分析 | Qwen2.5-7B-GPTQ-Int4 | ~4GB VRAM / 8GB RAM | ⚠️ 低配机器可能OOM |
| Embedding | bge-small-zh | ~200MB RAM | ✅ 轻量 |
| 云端增强 | 可选API | 按需 | ✅ 灵活 |

**风险识别**:
1. **7B模型OOM风险（高）**：大量企业用户用集成显卡或低配笔记本
   - **缓解**: 4-bit量化+动态加载+低配降级为0.5B-only模式
2. **模型首次下载大（中）**：7B模型约4GB，首次安装需下载
   - **缓解**: 分阶段下载（先0.5B，后台下载7B）
3. **模型推理延迟（中）**：7B在CPU上推理可能>5s/封
   - **缓解**: 批量处理+异步推理+缓存

#### 决策3: 产品形态（Outlook插件+独立客户端）

**评审结论**: ⚠️ 建议先做一个，不要并行

| 形态 | 技术复杂度 | 用户覆盖 | 建议 |
|------|-----------|----------|------|
| Outlook插件 | 高（需兼容Office JS API） | 高（企业用户） | P0 |
| 独立客户端 | 中（Electron/Tauri） | 中（跨平台） | P0 |
| Gmail插件 | 中 | 低（国内少） | P1 |
| Foxmail/163 | 低 | 低 | P2 |

**ENG建议**：
- **Phase 1**: 独立客户端优先（技术可控，跨平台）
- **Phase 2**: Outlook插件（企业市场刚需）
- **理由**：独立客户端可以更快验证PMF，插件开发周期长且受平台限制

## 3. 技术架构问题清单

### 3.1 数据流设计

**当前PRD问题**：数据流描述不够具体

**建议的数据流**：
```
新邮件到达
  ├── [同步引擎] 下载邮件 → 存储原始.eml
  ├── [解析引擎] 提取元数据（发件人/日期/主题/正文）
  ├── [0.5B分类] 5类分类 + 紧急度 → 写入分类标签
  ├── [规则引擎] 触发条件匹配 → 写入事件队列
  ├── [Embedding] 正文向量化 → 写入向量索引（异步）
  └── [7B分析] 仅重要邮件触发 → 实体提取/摘要（异步）

用户查询
  ├── [自然语言] → 语义检索（向量索引）
  ├── [结构化] → SQL查询（Postgres）
  └── [场景推荐] → 规则匹配 + 模型推理
```

### 3.2 存储设计

**建议的Schema（简化版）**：
```sql
-- 邮件主表
emails (
  id UUID PRIMARY KEY,
  message_id TEXT UNIQUE,
  thread_id TEXT,
  account_id UUID,
  from_name TEXT, from_email TEXT,
  to_list JSONB, cc_list JSONB,
  subject TEXT, body_text TEXT,
  date TIMESTAMPTZ,
  has_attachment BOOLEAN,
  category INT, -- 0-4: 审批/通知/讨论/汇报/其他
  urgency INT, -- 0-2: 高/中/低
  confidence FLOAT,
  created_at TIMESTAMPTZ
);

-- 向量索引（pgvector）
email_embeddings (
  email_id UUID PRIMARY KEY,
  embedding VECTOR(768)
);

-- 实体表
entities (
  id UUID PRIMARY KEY,
  email_id UUID,
  entity_type TEXT, -- person/company/project/amount/date
  entity_value TEXT,
  confidence FLOAT
);

-- 场景推荐记录
recommendations (
  id UUID PRIMARY KEY,
  user_id UUID,
  scene_type TEXT,
  trigger_condition TEXT,
  score FLOAT,
  status TEXT, -- shown/clicked/dismissed
  created_at TIMESTAMPTZ
);
```

| 风险 | 概率 | 影响 | 缓解措施 | 优先级 |
